# JASIM — UNIFIED GENERAL GENERATIVE RUNTIME

## READ, RECONCILE, IMPLEMENT — DO NOT HARDCODE THE EXAMPLES

اقرأ أولًا جميع الملفات والمستندات التي أرسلتها لك عن جاسم، بما فيها الملفان الأخيران، واقرأ الكود الحالي داخل `jasim-unified` قبل إجراء أي تعديل.

هذه الملفات ليست أوامر منفصلة لبناء أنظمة مختلفة، بل هي **مصادر معرفة معمارية متراكمة لنفس جاسم**.

المطلوب منك هو استخراج أفضل الأفكار منها، مقارنة ذلك بالكود الفعلي، ثم دمج ما هو صحيح ومفيد داخل النظام الحالي.

لا تنشئ JASIM جديدًا.
لا تنشئ مشروعًا موازيًا.
لا تعمل Fork للمعمارية.
لا تعيد بناء النظام من الصفر دون ضرورة.

`jasim-unified` هو الـCanonical Production Codebase.

---

# 1. الرؤية النهائية التي يجب تثبيتها

جاسم ليس:

* Marketplace ثابتًا.
* SaaS Builder ثابتًا.
* مجموعة تطبيقات جاهزة.
* مجموعة صفحات Domain-specific.
* مجموعة قوالب سيارات/مطاعم/وظائف/عقارات.
* Chatbot يجيب بالنص فقط.
* Bubble Renderer يعرض JSON جميلًا.
* مجموعة Agents منفصلة لكل مجال.

جاسم يجب أن يصبح:

> ONE CHAT + GENERAL INTELLIGENCE + UNIVERSAL CAPABILITIES + GENERATIVE COMMERCIAL RUNTIME

أي أن المستخدم يدخل من **واجهة محادثة رئيسية واحدة فقط**.

ومن هذه المحادثة يستطيع جاسم فهم الطلب، تخطيطه، تنفيذ ما يحتاجه، إنشاء البيانات والحالة والعمليات المطلوبة، ثم توليد الواجهة المناسبة ديناميكيًا.

# 2. الواجهة المعتمدة

الواجهة التي أعطيتك إياها هي الواجهة الأساسية المعتمدة لجاسم.

لا نريد تحويل جاسم إلى مجموعة صفحات تقليدية.

الصفحة الرئيسية هي:

> JASIM MAIN CHAT

ومنها تبدأ كل التجارب.

يجب الحفاظ على تصميم الواجهة المعتمدة وتطويرها تقنيًا دون تغيير فلسفتها أو تحويلها إلى Dashboard تقليدي.

يجب أن تدعم:

* محادثة جديدة.
* المحادثات السابقة.
* استعادة المحادثة.
* Streaming.
* الملفات والصور والمدخلات المختلفة.
* ظهور النتائج التوليدية داخل المحادثة.
* الانتقال إلى Bubble/World تم إنشاؤه.
* العودة للمحادثة.
* استمرار حالة العالم بعد العودة.
* تعدد العوالم التي أنشأها المستخدم.

لكن لا تبنِ صفحات ثابتة لكل نوع عالم.

# 6. افصل العقل عن البيئة

## Planner

## Capabilities

تعطي النظام اللبنات التنفيذية العامة.

# 11. Generality أهم من الأمثلة

> ACCEPTANCE TESTS

"أريد بيع سيارتي"

يجب ألا يوجد:

```ts
if (intent === "sell_car")
```

يجب أن يستنتج النظام مثلًا:


"أريد بيع معدات مطعمي"

أو:

"أريد عرض ماكينة صناعية للإيجار"

بدون إضافة كود Domain جديد.

# 40. Definition of Done

لا تقل:

> JASIM COMPLETE

إلا إذا كان لديك دليل على:

1. Main Chat واحدة تعمل فعليًا.
2. Runtime/Kernel موحد.
3. World persistence حقيقية.
4. Capability composition عامة.
5. Planner يعمل على Runtime الحقيقي.
6. DNA/Execution Graph قابل للتنفيذ.
7. Generative Bubble Runtime حقيقي.
8. Bubble actions تغير الحالة الحقيقية.
9. Chat يستطيع تعديل World موجود.
10. Restart recovery يعمل.
11. Policy/permissions تعمل.
12. Verification بعد التنفيذ يعمل.
13. لا يوجد Fake Success.
14. لا يعتمد النظام على Domain-specific bubbles.
15. اختبارات Generalization الجديدة تمر.
16. Regression Tests تمر.
17. Production Build يمر.
18. E2E حقيقي يمر.

# 42. قاعدة التطوير من الآن

أي تفاصيل جديدة سأرسلها لاحقًا عن:

* شكل الفقاعات.
* طريقة فتح العوالم.
* التنقل.
* المحادثات.
* المنصات.
* الذكاء داخل الفقاعات.
* البيع.
* الشراء.
* التوظيف.
* الخدمات.
* الدفع.
* الإعلانات.
* التسعير.
* العمولات.
* أو غيرها.

تعامل معها على أنها:

> Requirements فوق نفس Universal Runtime

ولا تحول كل Requirement إلى نظام مستقل.

الهدف النهائي ليس بناء جميع الأمثلة التي أعطيتها لك.

الهدف هو:

> بناء جاسم بطريقة تجعل الأمثلة التي لم أعطها لك ممكنة أيضًا.

ابدأ الآن بمرحلة:

**INSPECT + ARCHITECTURE RECONCILIATION**

ثم نفذ الإصلاحات الفعلية حسب Dependency Order.

لا تعلن النجاح قبل تشغيل النظام الحقيقي وإثباته.
