اعتمد تحديث المهمة #14 كما هو، وابدأ التنفيذ داخل نفس المهمة دون إنشاء Task مكررة.

المرحلة السابقة الخاصة بـMain Chat تعتبر Baseline مثبتًا:

```text
Web Main Chat → Conversation Turn
Mobile Main Chat → Conversation Turn
Message persistence → REAL
Automatic Task creation for every prompt → REMOVED
```

لا تعِد بناء هذه الطبقة ما لم يظهر Regression حقيقي.

# 1. الهدف الحالي

نريد الآن نقل جاسم من:

```text
TEXT / EPHEMERAL BUBBLE / SAFE INTERACTIVE BUBBLE
```

إلى Output Runtime عام يستطيع اختيار الشكل المناسب للهدف:

```text
TEXT
STRUCTURED_RESULT
EPHEMERAL_BUBBLE
INTERACTIVE_BUBBLE
DIRECT_ACTION
WORKFLOW
DURABLE_RUN
PERSISTENT_SMART_BUBBLE
```

لكن بدون السماح للنموذج بتنفيذ Side Effects أثناء التصنيف.

# 2. Output Router هو مصنف ومخطط أولي، وليس Executor

المسار الصحيح:

```text
User Turn
↓
Model Gateway
↓
Proposed Output Envelope
↓
Schema Validation
↓
Semantic Validation
↓
Runtime Feasibility Check
↓
Capability Availability Check
↓
Output Form Accepted / Downgraded / Blocked
```

ولا:

```text
Model chooses ACTION
↓
external execution immediately
```

# 3. النموذج غير موثوق

تعامل مع كل مخرجات النموذج كـUntrusted Input.

تحقق من:

```text
outputType
requiredCapabilities
target references
requested persistence
risk level
required inputs
```

ولا تسمح للنموذج بإرسال:

```text
provider function name
arbitrary code
ownerId
permission override
approval bypass
raw database operation
```

# 4. Semantic Output Envelope

وسع العقد الحالي ليكون قادرًا على وصف النتيجة المقترحة مثلًا:

```text
outputType
summary
structuredPayload?
bubbleProposal?
runProposal?
actionProposal?
requiredCapabilities[]
missingInputs[]
references[]
persistenceIntent
confidence / ambiguity metadata
```

استخدم تصميم المشروع الحالي الأنسب، ولا تعتبر هذا Schema حرفيًا إلزاميًا.

# 5. لا تخلق Task تلقائيًا عند DIRECT_ACTION

إذا كان المستخدم يقول:

> بع هذا الهاتف.

لا يجب أن يكون القرار:

```text
DIRECT_ACTION
↓
create Task + World automatically
```

يمكن أن ينتج:

```text
Run
```

أو execution intent مناسب.

# 6. Durable Run — كيان مستقل حقيقي

أنشئ/أكمل `Run` كـAggregate دائم مستقل عن `Task`.

يجب أن تستطيع Run أن توجد بدون:

```text
bubbleId
worldId
taskId
```

عند عدم الحاجة.

العلاقات يجب أن تكون اختيارية حسب الحالة.

مثال مفاهيمي:

```text
Run
- id
- ownerId
- conversationId?
- bubbleId?
- taskId?
- goal
- status
- executionGraph?
- currentState
- requiredCapabilities
- idempotencyKey
- createdAt
- updatedAt
- resumeAt?
```

استخدم أسماء المشروع الحالية إن كانت أفضل.

# 7. Run ليست Bubble

مثال:

> راقب سعر هذا المنتج.

يمكن أن ينتج:

```text
DURABLE_RUN
```

بدون Smart Bubble دائمة.

# 8. Run ليست World

مثال:

> بع سيارتي.

قد تحتاج عملية تستمر عدة أيام:

```text
collect data
prepare listing
publish
monitor replies
request approval
resume
```

لكن هذا لا يعني إنشاء World كامل.

# 9. Run ليست Task القديمة بشكل اسم جديد

قبل تنفيذها، افحص Task الحالية.

حدد الفرق الواضح في المسؤولية:

```text
Task = unit of planned work / existing runtime abstraction
Run = durable execution instance / lifecycle
```

إذا كان يمكن توسيع abstraction الحالية بأمان دون ازدواجية، افعل ذلك.

لا تنشئ طبقتين تؤديان نفس الوظيفة.

لكن لا تجبر كل Run على الارتباط بـWorld أو Bubble فقط لأن Task الحالية تفعل ذلك.

# 10. Run lifecycle

صمم lifecycle عامة وقابلة للتوسع، مثل:

```text

completed

```

لا يلزم استخدام نفس الأسماء إذا كان المشروع لديه حالات Canonical بالفعل.

# 12. Idempotency

كل إنشاء أو Transition حساسة لـRun يجب أن تحترم Idempotency.

اختبر:

```text
same request twice
client retry
parallel create
server retry
```

ولا تنشئ Run مكررة دون سبب.

# 13. Ownership

User A لا يستطيع:

```text
read
resume
cancel
modify
approve
inspect events
```

Run تخص User B.

اختبر ذلك على الخادم، وليس UI فقط.

# 14. Restart durability

اختبر:

```text
Create Run
↓
persist
↓
restart API
↓
read Run
```

ويجب أن تعود بنفس الحالة.

# 15. لا تضف Worker execution الحقيقي قبل تثبيت العقود

في هذه المرحلة يمكن تأسيس:

```text

state
events

```

قبل تفعيل أي Provider خارجي.

لكن لا تسجل نجاحًا خارجيًا وهميًا.

# 16. DIRECT_ACTION يجب ألا يعني Side Effect أثناء التصنيف

إذا اختار Router:

```text
DIRECT_ACTION
```

فالناتج في هذه المرحلة هو:

```text

```

وليس:

```text

```

# 17. Workflow output

# 22. Downgrade behavior

```text

```

```text

```

أو downgrade إلى plan/structured response إذا كان ذلك صادقًا ومفيدًا.

لا تحول الطلب إلى Bubble فقط لتجنب الحجب.

# FINAL RULE

ثبت معماريًا:

> Jasim decides what kind of runtime the user's goal needs before deciding how to execute it.

> A direct action does not require a platform.

> A durable run does not require a Bubble.

> A Smart Bubble does not require a World unless durable world state is actually needed.

> The model proposes. The Runtime validates. Only trusted execution layers may perform side effects.

ابدأ الآن تنفيذ هذه المرحلة داخل المهمة #14، اختبرها، أصلح أي Regression، ثم انتقل تلقائيًا للمرحلة التالية من برنامج الإكمال.
