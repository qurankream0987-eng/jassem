## 0. PURPOSE OF THIS DOCUMENT

Read this document as an architectural teaching specification.

The purpose is to make the intended meaning of BLOCK 1 unambiguous
before implementation begins.

Do NOT interpret the scenarios below as separate product features.

Do NOT create one service, router, workflow, schema, UI component,
agent, or database table per example.

The examples are acceptance scenarios for ONE universal architecture.

BLOCK 0 has already closed the Kernel trust and recovery gate.

Therefore BLOCK 1 must NOT redesign:

- authentication
- cross-owner isolation
- Trusted Executor
- Attempt Ledger
- Verifier
- Reconciliation
- Run recovery
- worker leases
- migration infrastructure
- readiness infrastructure

Those are accepted foundations.

BLOCK 1 asks a different question:

Can JASIM take an open-ended user goal that was not explicitly
programmed in advance and transform it into:

SEMANTIC STATE
+
GENERAL CAPABILITIES
+
A VALIDATED COMPOSITION
+
THE CORRECT INTERACTION SURFACE
+
GENERAL ECONOMIC RELATIONSHIPS WHEN RELEVANT

without adding domain-specific Core code?

# =====================================================================
# 2. BLOCK 1 HAS THREE INTERNAL FABRICS
# =====================================================================

BLOCK 1 contains three conceptual fabrics.

They are separated for architectural clarity, but they cooperate in
the same runtime.


---------------------------------------------------------------------
PHASE 1 — UNIVERSAL CAPABILITY FABRIC
---------------------------------------------------------------------

This phase answers:

WHAT MUST JASIM BE ABLE TO DO
TO ACHIEVE THE USER'S GOAL?


It introduces or completes the general semantic path:

Goal
→ Outcomes
→ Capability Requirements
→ Registered Capabilities
→ Composition
→ Typed Execution DAG


It must NOT create domain workflows.

It should behave more like a semantic compiler than a collection
of agents.

# =====================================================================
# 3. PHASE 1 — UNIVERSAL CAPABILITY COMPILATION
# =====================================================================

A User Goal is not an executable instruction.

For example:

"Sell my phone."

must NOT immediately become:

SellPhoneWorkflow.


Instead JASIM should derive a Semantic Goal.


Conceptually:

SemanticGoal {
    actor
    intent
    references
    desiredOutcomes
    hardConstraints
    softPreferences
    temporalContext
    locationContext
    economicContext
    riskSignals
}


The Semantic Goal is then decomposed into Desired Outcomes.

For example:

"Sell my phone"

may require:

a structured subject exists

an Offering exists

minimum required information exists

the owner authorizes publication

a discoverable public projection exists


Only after the outcomes are understood should JASIM derive:

Capability Requirements.


For example:

RESOLVE_ENTITY

STRUCTURE

CREATE_OFFERING

ATTACH_ARTIFACT

PUBLISH


These requirements are semantic.

They are NOT automatically trusted executable capabilities.


# =====================================================================
# 4. CAPABILITY REQUIREMENT VS TRUSTED CAPABILITY
# =====================================================================

This distinction is mandatory.


A Capability Requirement means:

"This goal requires this kind of operation."


A Registered Capability means:

"The trusted server runtime has an approved, versioned contract capable
of performing this operation."


The LLM may propose:

CONTROL_DEVICE

as a requirement.


The LLM may NOT automatically register:

FactoryRobotController


and execute it.


If no trusted general capability satisfies the requirement:

MISSING_GENERIC_CAPABILITY


is the truthful result.


This is a successful architectural diagnosis.

It is NOT a reason to create domain code during an acceptance test.


# =====================================================================
# 5. CAPABILITY DEFINITIONS MUST BE CONTRACTS
# =====================================================================

A capability is not merely a string such as:

SEARCH

TRACK


It must have trusted semantics.

Conceptually, a Capability Definition may contain equivalents of:

Do NOT implement this exact structure if equivalent canonical contracts
already exist.

Map the requirement onto existing JASIM structures first.

REUSE BEFORE CREATE.


# =====================================================================
# 6. FOUR IMPORTANT CAPABILITY CLASSES
# =====================================================================

Capability semantics should distinguish at least these conceptual
classes.


PURE / ANALYTICAL

Examples:

ANALYZE

These generally do not create an external side effect.


INTERNAL STATEFUL

Examples:

CREATE_ENTITY

UPDATE_NEED

CREATE_ENGAGEMENT

EXTERNAL EFFECTFUL

Examples:

PAY

BOOK_EXTERNALLY
DELIVER
DEVICE_CONTROL
EXTERNAL_APPLICATION


These cross the trusted external effect boundary.

They must eventually use the canonical Trusted Executor.


HUMAN / AUTHORITY BOUND

Examples:

OWNER_APPROVAL
SIGNATURE
MEDICAL_DECISION
BUSINESS_POLICY_DECISION
REGULATORY_AUTHORIZATION


These are not automatically executable provider calls.

The Capability Requirement Graph may contain a Human Decision Gate.


# =====================================================================
# 7. CAPABILITY COMPOSER / COMPILER
# =====================================================================

The Composer must not simply retrieve a workflow by name.

Its role is:

Given:

CURRENT STATE

DESIRED OUTCOMES

CAPABILITY REQUIREMENTS

REGISTERED TRUSTED CAPABILITIES

SCHEMAS

PERMISSIONS

PROVIDER AVAILABILITY

RESOURCE AVAILABILITY

POLICY

find the smallest valid composition capable of moving the runtime from
the current state toward the desired state.


The Composer should be able to distinguish:

logical requirements

from:

actual executable nodes.


A Capability Requirement Graph may contain:

branches

joins

conditions

human gates

provider requirements

resource requirements


The final Execution DAG may contain only:

registered capability identities

validated inputs

typed bindings

approved policies

known execution semantics


# =====================================================================
# 8. TYPED BINDINGS ARE MANDATORY
# =====================================================================

BLOCK 1 must not become prompt chaining.


Forbidden architecture:

Capability A
→ arbitrary LLM text
→ Capability B
→ provider


Required architecture:

Capability A
→ validated structured output
→ typed binding
→ Capability B input


Example:

DISCOVER

produces:

CandidateOffering[]


MATCH

requires:

CandidateOffering[]
+
NeedExpression


If the schemas do not match:

BINDING_VALIDATION_FAILED


If transformation is required, it must be explicit:

SEARCH
→ EXTRACT
→ NORMALIZE
→ VALIDATE
→ MATCH


No hidden semantic transformation should be allowed to cross a trusted
effect boundary.


# =====================================================================
# 9. GAP CLASSIFICATION
# =====================================================================

BLOCK 1 must distinguish different reasons why a goal cannot proceed.


MISSING_GENERIC_CAPABILITY

The semantic primitive does not exist.


BLOCKED_BY_PROVIDER

The capability exists but no trusted provider is available.


BLOCKED_BY_RESOURCE

The capability and provider may exist, but the required real-world
resource does not exist or is unavailable.


REQUIRES_HUMAN

A human decision or intervention is required.


REQUIRES_OWNER_DECISION

The owner must make a business or policy decision.


REQUIRES_REGULATORY_REVIEW

A regulatory or professional authority is required.


INSUFFICIENT_INFORMATION

Required typed input is missing.


INSUFFICIENT_TRUST

The information exists but does not meet required trust or verification
thresholds.


These states must not silently become success.


# =====================================================================
# 10. PHASE 2 — GENERATIVE INTERACTION
# =====================================================================

The user should never be forced to interact with raw Runtime objects.

The runtime should project state into the smallest useful interaction
surface.


The governing principle is:

SMALLEST SUFFICIENT SURFACE.


Examples:

simple factual result
→ TEXT / STRUCTURED RESULT

multiple candidates
→ LIST

comparative decision
→ COMPARISON

missing structured input
→ FORM

one object
→ DETAIL

current state
→ STATUS

historical process
→ TIMELINE

trackable entity
→ TRACKER

trusted geospatial observation
→ MAP

time-oriented information
→ CALENDAR / SCHEDULE

sensitive transition
→ APPROVAL

trusted external provider transition
→ EXTERNAL ACTION

persistent operational system
→ SMART BUBBLE


Do not generate a persistent Bubble when a status card is sufficient.

Do not generate a World when a transient form is sufficient.

Do not generate a map merely because tracking is involved.

# =====================================================================
# 13. UI IS A PROJECTION, NEVER THE SOURCE OF TRUTH
# =====================================================================

Canonical runtime state is authoritative.

For example:

delivery.status = ASSIGNED

may be rendered as:

a Status Card

a Timeline

a Tracker

or a Map


The user interface must not independently update business truth.

Buttons generate intents.

They do not directly execute trusted effects.


Correct:

UI Action
→ Action Intent
→ Canonical Runtime
→ Policy
→ Mutation / Execution


Incorrect:

Button
→ provider adapter directly


# =====================================================================
# 14. TRACKER AND MAP MUST BE SEPARATED
# =====================================================================

TRACKING is semantic.

MAP is presentation.


A shipment may be trackable without real coordinates.

For example:

Last trusted observation:
Warehouse A
20 minutes ago
Customs cleared


This can be rendered as a Tracker.

If trusted coordinates exist:

Tracker + Map may be appropriate.


Never fabricate:

GPS coordinates

movement

route

ETA

arrival state


because the UI "looks better" with them.


# =====================================================================
# 15. EXTERNAL ACTION FOUNDATION
# =====================================================================

JASIM must not attempt to replicate every external system.

Certain actions should transition the user into an approved external
provider experience.

Examples:

payment checkout
OAuth authorization
identity verification
government portal
merchant checkout
external job application
shipping portal
bank authorization


Use a general concept equivalent to:

ExternalActionIntent


The server should create an authorized:

ExternalActionSession


Conceptually bound to:

owner
purpose
provider
related Run
related transaction if applicable
nonce/state
expiry
return correlation


The LLM must NEVER be allowed to generate an arbitrary URL and have that
URL treated as trusted execution.


Use:

HTTPS
trusted/approved origins
purpose binding
owner binding
short expiry
single-use semantics where needed
state/nonce validation


The browser is presentation.

The browser is NOT transaction truth.


# =====================================================================
# 16. PHASE 3 — ECONOMIC VALUE NETWORK
# =====================================================================

BLOCK 1 must not implement a traditional marketplace architecture.

Do not reduce the system to:

Product
Seller
Buyer
Order


Instead model general value exchange.


An ENTITY represents what exists.


An OFFERING represents:

what an actor/entity/resource makes available to others under conditions.


A NEED represents:

what an actor/entity requires under constraints.


A MATCH represents:

a structured compatibility relationship between Need and Offering.


An ENGAGEMENT represents:

an actual relationship opened between participants.


A PROPOSAL represents:

versioned structured terms proposed within that relationship.


A TRANSACTION INTENT represents:

an accepted intention to execute value exchange.


# =====================================================================
# 17. ENTITY IS NOT OFFERING
# =====================================================================

Example:

Warehouse #82

is an Entity / Resource.


The owner saying:

"5 tons of refrigerated capacity are available next week"

creates an Offering.


The Warehouse may later create:

another Offering

with:

different dates
different capacity
different terms


Therefore:

ENTITY != OFFERING


The same applies to:

Person
Vehicle
Machine
Generated Bubble
Company
Skill
Property
Digital capability


# =====================================================================
# 18. OFFERING IS GENERAL VALUE AVAILABILITY
# =====================================================================

An Offering may represent:

physical product

service

skill

time

capacity

access

employment opportunity

delivery capacity

rental capacity

digital output

subscription

generated Smart Bubble capability

barter value

free resource

future unknown economic value


Do not create Core tables for each of these.


# =====================================================================
# 19. NEED IS NOT A SEARCH STRING
# =====================================================================

A Need must become structured runtime state.

For example:

"I need refrigerated storage for two tons for one week."


should become semantics equivalent to:

requirement:
refrigerated storage capacity

hard constraints:
capacity >= 2 tons
duration >= 7 days

soft preferences:
near desired region
reasonable price

timing:
specified period


This allows deterministic matching and future persistence.


# =====================================================================
# 20. OFFERING AND NEED MAY BOTH APPLY TO THE SAME ACTOR
# =====================================================================

Example:

"Employ me."


The person may have:


Offering:

React development capability
availability
experience


Need:

employment opportunity
minimum salary
location preference


Likewise, an employer may have:


Need:

React capability


Offering:

employment compensation and opportunity


This is more general than a traditional Job Marketplace.


# =====================================================================
# 21. MATCHING
# =====================================================================

Matching must be explainable.


Do NOT use:

"93% AI Match"

as the only meaning.


For each relevant constraint, matching should conceptually preserve:

PASS

SOFT_MATCH

UNKNOWN

FAIL


Example:

React experience >= 3 years
→ PASS

salary <= 1500
→ PASS

available next week
→ UNKNOWN

verified certification
→ UNKNOWN


Unknown must remain Unknown.

It must not silently become PASS or FAIL.


# =====================================================================
# 22. HARD CONSTRAINTS BEFORE SEMANTIC RANKING
# =====================================================================

Required pipeline:

Candidates
→ structured hard constraint filtering
→ semantic compatibility
→ preference ranking
→ deeper reasoning on small candidate set if useful


Example:

User requires:

price <= 4000


A semantically excellent result costing 7000 must not outrank valid
candidates merely because its embedding similarity is high.


This is both a correctness rule and a cost-control rule.


# =====================================================================
# 23. MATCHING MUST SUPPORT COMPOSITION
# =====================================================================

A Need does not always require exactly one Offering.


Example:

Need:

10 tons refrigerated capacity


Available:

Offering A = 6 tons

Offering B = 4 tons


If:

splitAllowed = true

then JASIM may produce a Composite Match.


If:

singleFacilityRequired = true

then the same pair fails.


The architecture must not assume:

Need 1 ↔ Offering 1 only.


# =====================================================================
# 24. DISCOVERY MUST BE AUTHORIZED
# =====================================================================

Visibility semantics should support equivalents of:

PRIVATE

UNLISTED

SHARED

PUBLIC


PRIVATE:

never appears in general discovery.


UNLISTED:

only accessible through an explicit reference or permitted path.


SHARED:

visible only to authorized participants/groups.


PUBLIC:

eligible for general discovery according to policy.


Do NOT default newly generated Bubble state, Offering state, or Need state
to PUBLIC.


# =====================================================================
# 25. PUBLICATION IS A STATE TRANSITION
# =====================================================================

Publishing is not merely:

isPublic = true


It should conceptually follow:

Publication Intent
→ Reference Resolution
→ Owner Authorization
→ Privacy/Projection Validation
→ Visibility Mutation
→ Version
→ Discoverable Projection
→ Event


The LLM may recommend publication.

It must not silently make private state public.


# =====================================================================
# 26. GENERATED BUBBLES MAY BECOME ECONOMIC OFFERINGS
# =====================================================================

Example:

User A says:

"Build me a system that connects office-cleaning companies with offices."


JASIM creates:

Persistent Smart Bubble / World


Initially:

PRIVATE


Later User A says:

"Make this service available to people."


JASIM should NOT build another application.


The same generated system may produce an authorized:

PUBLIC OFFERING PROJECTION


Later User B says:

"I need my office cleaned every Thursday."


JASIM should be able to:

create Need
→ discover public capability
→ match the generated Bubble
→ present the relevant interaction


User B does not need to know:

the Bubble name
the Bubble ID
the creator
the implementation details


This is a critical architectural objective.


# =====================================================================
# 27. PUBLIC PROJECTION MUST NOT EXPOSE PRIVATE WORLD STATE
# =====================================================================

A generated business Bubble may internally contain:

customers
staff
private messages
financials
internal metrics
orders
profit margins


Publishing its service must NOT publish the whole World.


Required:

Private Runtime State
→ Publication Policy
→ Authorized Public Projection
→ Discovery


The renderer receives only authorized projection data.


Security must not depend on merely hiding fields in the UI.


# =====================================================================
# 28. ENGAGEMENT
# =====================================================================

A Match is not yet a relationship.


If the user says:

"Contact the second one."

or:

"Negotiate with this seller."


JASIM may create an Engagement.


Conceptually:

Engagement {
    participants
    context
    sourceNeed
    sourceOffering
    matchRef
    permissions
    proposalRefs
    sharedArtifacts
    state
}


Do not create:

BuyerSellerEngagement

EmployerCandidateEngagement

TenantLandlordEngagement


Use generic participants and contextual semantic roles.


# =====================================================================
# 29. PROPOSAL IS STRUCTURED STATE, NOT ONLY A CHAT MESSAGE
# =====================================================================

Seller:

# =====================================================================
# 30. TRANSACTION INTENT
# =====================================================================

PAYMENT_SETTLED

PROPOSAL_ACCEPTED
!=
DELIVERY_COMPLETED

PROPOSAL_ACCEPTED
!=
BOOKING_CONFIRMED


BLOCK 1 should stop at a general:

when execution requires later operational or financial fabrics.


TransactionIntent may represent:

sale

service

rental

booking

employment

application

subscription

exchange

B2B order

access agreement

future unknown exchange types


Payment must NOT be mandatory.
