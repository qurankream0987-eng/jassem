# JASIM — سطحٌ واحد مخزون، راسمان يقرآنه، وشخصٌ يراه مرّتين

`CANONICAL_PRESENTATION_STATE != VISIBLE_RENDER_INSTANCE`

---

## 1. ما لم يكن هو التكرار في التخزين

ستّة عروضٍ قانونية، **مجموعة نتائج واحدة**، وشبكتان وإثنتا عشرة بطاقة.
والسبب ليس نسختين محفوظتين. السطح **محفوظٌ مرّةً واحدة** في
`messages.metadata.presentation`، و`getActiveWorkspaceProjection` **تقرؤه من هناك**:

```ts
const currentPresentation = presentationFromMessage(latestMessage?.metadata);
```

فالورشة ليست مَخزناً ثانياً، بل **إسقاطٌ لآخر رسالة**. والراسمان — فقاعة الرسالة
(`ChatMessage.tsx`) والورشة (`ActiveGenerativeWorkspace.tsx`) — **يقرآن نفس البايتات من
نفس الصفّ**. ولمّا نقلت مرحلةُ `a8c4e31` الورشةَ إلى داخل مجرى المحادثة، صارت النسختان
واحدةً تحت الأخرى.

## 2. ولماذا لا يُحَلّ بالشكل

```
VISUAL_EQUALITY_USED_FOR_DEDUPE = 0
JSON_EQUALITY_USED_FOR_DEDUPE   = 0
```

دورانِ متتاليان على نفس العروض يُنتجان سطحَين **متطابقَين بايتاً ببايت**، وهما سطحان
حقيقيان ويجب أن يظهرا كلاهما. فالمقارنة بالشكل كانت ستحذف أحدهما.

## 3. القاعدة

```
ONE SEMANTIC PRESENTATION -> ONE VISIBLE OWNER -> ONE VISIBLE INSTANCE
```

- **الإسقاط يُسمّي السجلّ الذي يعرضه**: حقلٌ واحد جديد، `currentPresentationSource`.
- **المضيف يُعلن** ما يرسمه فعلاً — وفقط حين يرسمه: لا وهو مطويّ، ولا بائت، ولا فاشل،
  ولا فارغ، ويُطلِقه عند الانصراف.
- **السجلّ المُطالَب به لا يرسم نفسه ثانيةً** في مكانه من المحادثة.

وليس «واحدةً لكل محادثة»: المضيف يعرض **الأخيرة**، فكل دورٍ سابق يحتفظ بسطحه حيث صنعه.
ثلاث عروضٍ متمايزة = ثلاث أسطح، كلٌّ مرّةً واحدة — **والتاريخ سليم**.

## 4. ولماذا احتفظ المضيفُ بالسطح الحيّ، لا الفقاعة

قرارٌ من الكود لا من الذوق. مسار الورشة:

```
source: 'WORKSPACE' · expectedPresentationVersion · idempotencyKey · SUBMIT_INPUT
```

أي **حارسُ بياتٍ** يرفض فعلاً مُوجَّهاً إلى سطحٍ تغيّر، وإرسالُ نماذج. أمّا مسار الفقاعة
فيشترط فقاعةً ذكيّةً مُسجَّلة، وبدونها ينتهي إلى `toast`. فإبقاء السطح الحيّ في الفقاعة كان
سيترك **أزراراً لا تفعل شيئاً** — وهو بالضبط الإخفاق المنهيّ عنه.

## 5. ولا شيء قانونيّ حُذف

```
CANONICAL_PRESENTATION_DELETED_TO_FIX_UI = 0
SECOND_PRESENTATION_STATE_STORE_ADDED    = 0
NEW_PRESENTATION_RUNTIME = NO · NEW_PRESENTATION_TABLE = NO
```

الصفّان يحتفظان بسطحيهما بعد دورَين — مُثبَتٌ بقراءة الجدول. المُضاف **حقلُ هويّةٍ واحد**،
ومتغيّرُ حالةٍ واحد في الواجهة يحمل مُعرِّف سجلّ. لا مخزن، لا جدول، لا راسم ثانٍ.

## 6. والحقل اختياريّ عمداً — وقد علّمني ذلك اختبارٌ موروث

أوّل صياغةٍ جعلته **مطلوباً**، فصار إسقاطٌ لا يحمله **غيرَ قابلٍ للتحليل أصلاً**، وسقط
اختبار تكافؤ الجوّال الموروث. والعيب في تغييري لا في الاختبار:

```
AN ABSENT CLAIM IS NOT AN INVALID PROJECTION
```

فمطالبةٌ غائبة تعني «لا أحد يعرضه»، والنتيجة أن يعود السطح إلى مكانه في المحادثة — وهو
الاتجاه الآمن. أمّا رفض الإسقاط كلّه فكان سيُفرِغ الورشة بسبب حقلٍ وظيفتُه إزالة تكرار.

## 7. ما قِيس في متصفّحٍ حقيقي

| | قبل | بعد |
|---|---|---|
| شبكات لمجموعة نتائج واحدة | **2** | **1** |
| بطاقات | **12** | **6** |
| بعد إعادة التحميل | — | 1 / 6 |
| بعد المغادرة والعودة | — | 1 / 6 |
| ثلاثة أسطح متمايزة | — | 3 شبكات، 0 مكرّرة |
| عناصر مخفيّة حاضرة للقارئ الصوتي | — | **0** |

```
MOBILE_390X844 = PASS   MOBILE_430X932 = PASS   DESKTOP_1440X900 = PASS
HORIZONTAL_PAGE_SCROLL = 0   COMPOSER_USABLE = PASS
```

السطح المُطالَب به **غير مرسومٍ أصلاً**، لا مخفيٌّ بـCSS — فلا يبقى في شجرة الوصول ولا في
ترتيب التنقّل.

## 8. ما بقي صادقاً

**لا مرشّح اكتشافٍ يحمل فعلاً اليوم.** `normalizeCandidate` هي الكاتب الوحيد لـ`actionable`
وتكتب `[]` دائماً — للداخليّ والخارجيّ معاً. فعدد الأزرار في كل بطاقات الاكتشاف **صفر**،
قبل هذه المرحلة وبعدها. وقد أُثبِت أنّ المضيف الباقي **يُركّب الزرّ ومرجعَه القانونيّ** حين
يُعطى فعلاً، لكنّ المسار الذي يملأ `actionable` من قدرةٍ حقيقية غير موجود.
