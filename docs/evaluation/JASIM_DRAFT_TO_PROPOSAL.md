# JASIM — إرسال المسودّة التي راجعتَها بالضبط

`PROPOSAL != AGREEMENT != COMMITMENT != TRANSACTION != PAYMENT`

---

## 1. الفجوة

كان المرءُ يختار، ويراجع الشروط المُثبَّتة بالضبط — **ولا يملك زرّاً يرسلها**. مسارُ
`CREATE_PROPOSAL` كان `unavailableRoute`، وأنواعُ مراجعه تشغيلاتٌ ومهامّ، وحمولتُه نصُّ هدف.
والكلامُ وحده يبلغ `proposeTurn`.

## 2. وقتُ واحد، مدخلان

```
SECOND_PROPOSAL_RUNTIME_ADDED = 0
```

استُخرِج `proposeCommercialOrder` من جسد `proposeTurn` — لم يُنسَخ. ويُثبِته الاختبار بقراءة
الكود: **نداءٌ واحد** لـ`proposeTermSheet` في المُنسِّق كلّه، ولا ذِكرَ له في المُرسِل.

وجسدُه **لا يقرأ مُغلّفاً** أصلاً، فالضغطةُ تستدعيه بلا نيّةِ نموذجٍ مُختلَقة:

```
BUTTON_PROPOSAL_REQUIRES_MODEL = NO
```

## 3. السباق — مُثبَتٌ بإزالة القفل، لا بالثقة بتعليق

فحصُ «أُرسِل بالفعل» يقرأ `proposalId`، والكتابةُ تضعه **بعد ذلك بكثير**. فأمرَ الطور أن
نُثبِت لا أن نفترض — فأزلتُ القفل وأعدتُ التشغيل:

```
بلا قفل:  إرسالان متزامنان  →  عرضان  (expected 2 to be 1)
مع القفل: إرسالان متزامنان  →  عرضٌ واحد
```

والتعليقُ الذي كان يقول «idempotent» **كان خاطئاً**. والقفل قفلُ Postgres نفسه، لكل طلب، يُؤخَذ
للمعاملة ويُطلَق معها.

## 4. النسخةُ التي يرتبط بها الزرّ

```
commercial_order:<termsVersion>:<termsFingerprint>:<configurationFingerprint>
```

لأنّ **ثلاثةَ أشياء تتحرّك مستقلّةً** وكلُّها تغيّر ما يوافق عليه المرء. وضبطُ المرء لشروطه
يكتب بصمتَه الخاصّة و**لا يرفع `termsVersion`** عمداً — فنسخةٌ من الشروط وحدها كانت ستسمح
بإرسال مسودّةٍ أُعيد ضبطها من مراجعةِ ما قبلها.

```
OLD_CONFIGURATION_REVIEW_PROPOSES = 0
```

## 5. الهويّة لا «الحاليّ»

الزرّ يحمل **معرّف الطلب بعينه**. والربطُ الفاعل شرطٌ **إضافي** (`requireCurrent`)، لا بديلٌ عن
الهويّة — فلا سباقَ بين ما رُوجِع وما أُرسِل.

```
BUTTON_REVIEWED_ORDER_DIFFERS_FROM_SENT_ORDER = 0
STALE_A_BUTTON_SENDS_B = 0
```

## 6. والحمولة فارغة — ويُرفَض ما سواها

المسودّةُ **تحمل شروطها**. فضغطةٌ تحمل شيئاً تُرفَض بدل أن تُجرَّد بصمت، لأنّ التجريد الصامت
هو كيف يظنّ المُنادي أنّ ما أرسله عمل.

```
CLIENT_SUPPLIES_PROPOSAL_TERMS = 0
COMMERCIAL_ORDER_PROPOSAL_PAYLOAD_CONTAINS_GOAL = 0
```

ومسارُ `{goal}` القديم للتشغيلات والمهامّ **باقٍ** كما كان.

## 7. و`propose` لا يستطيع مرشّحٌ أن يُعلنه

النيّة **ليست** في `SURFACE_INTENTS` — المُرشِّح الذي تمرّ منه نيّاتُ المرشّحين. فالإرسال لا
يُبلَغ إلّا من مسودّةٍ بين يدي صاحبها.

## 8. عيبان قديمان ظهرا في الطريق

- **`renderDetail` لم يُمرّر `onAction` قطّ**: كان يستدعي البطاقة بوسيطٍ واحد، فشرطُها
  `onAction && schema` لا يتحقّق أبداً. أيُّ سطح `DETAIL` كان يحمل فعلاً مُعلَناً **ولا يرسم له
  شيئاً** — في كلّ مكان، لا هنا فقط.
- **السطح كان يختفي عند الإرسال**: `draftAwaitingReview` كانت تُسقِط الطلب فور وجود
  `proposalId`، فيعود المرء إلى شبكة البحث لحظةَ ضغطه «إرسال». صار **نفسُ السطح** يعرض
  «بانتظار ردّ الطرف الآخر» بلا زرّ — لا سطحَ «مُرسَل» ثانٍ يُبقى متوافقاً.

## 9. ما قِيس في متصفّحٍ حقيقي — عالمٌ نظيف لكل مقاس

```
المراجعة  DETAIL · زرٌّ واحد «إرسال العرض»
بعد الضغط DETAIL · «بانتظار ردّ الطرف الآخر» · صفر أزرار
economic_proposals = 1   agreements = 0   transactions = 0   payment_intents = 0
السيناريو الثاني: اختيار 3 ثم 5 ثم إرسال → المُرسَل هو **5**، لا 3
MOBILE_390X844 = PASS  MOBILE_430X932 = PASS  DESKTOP_1440X900 = PASS  hScroll = 0
```

## 10. وتوقّعان موروثان استُبدلا — بالتعليل الرباعيّ

كلاهما كان يقول «لا زرّ في المراجعة»، **وكان صادقاً حين كُتب**: لم يكن ثمّة مسارٌ موثوق. وهذا
الطور غيّر المقدّمة ببناء المسار. فالقديم يُثبِّت المنتجَ على قدرةٍ ناقصة — يمرّ فقط ما دامت
المراجعة غيرَ صالحة — ويُثبِت **غيابَ ميزة** لا صحّةَ واحدة. والبديل أشدّ: زرٌّ واحد بالضبط،
نيّتُه يوجّهها المُرسِل فعلاً، يعمل على المرجع القانونيّ للمسودّة، ويختفي بعد الإرسال.
